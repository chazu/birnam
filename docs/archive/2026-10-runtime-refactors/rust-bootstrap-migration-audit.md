# Remaining Rust modules and cold bootstrap

> Archived 2026-10-30. Historical decisions, implementations and measurements;
> not current architectural authority or a work queue. Statements such as
> “current,” “required,” and “remaining” describe the recorded period.
> Use [Birnam invariants](../../../INVARIANTS.md) for current requirements.

Audit date: 2026-10-10. Baseline: `c072e3ac`, before the Trace port.

Update 2026-10-18: [source-registry ownership](../../design/authored-source-registry.md) has
moved from Generation into an early authored owner, including cold bootstrap.
No native registry seed remains. Candidate preparation/activation/undo policy has
also moved to Birnam; native artifact admission/mapping and optional certification
remain. The historical counts and dependency assessments below are not a current
crate inventory. Relational migration remains paused.

Update 2026-10-19: the next release requires a
[Store-independent core](store-independent-core-completion.md). Follow that
source-backed dependency plan before selecting further native module rewrites.
It does not require porting Store/Relational or every remaining native owner.

The recommended next rewrites are Trace, Relational, ProjectBuild and HostProject.
They contain behavior that can live in Birnam without replacing the compiler's
cold-bootstrap seed. Compiler, value and execution implementations need a
different treatment: production behavior can move to Birnam, but their bootstrap
implementations cannot yet disappear.

Retain Rust currently required to build and start from a clean checkout. Track
authored production implementations separately from retained bootstrap seeds.
Renaming surplus native code does not complete a port.

**Goal clarification, 2026-10-11:** the intended endpoint is complete Birnam
bootstrapping, with the ability to discard the Rust codebase. The Rust runtime
floor and seeds described below are current dependencies, not permanent design
commitments. Migration decisions must retain a path to implementing their
responsibilities in Birnam. Native machine code generated by Birnam is distinct
from permanently maintaining an implementation written in another language.

Environment lookup itself is cheap, so its relative overhead could rise; its

and retirement boundaries), value collections (language-wide hot paths), and
ProjectBuild (larger transactional publication surface) until after these small
candidates. No further port is started by this prioritization.

## Inventory and measurement

The baseline has 51 workspace crates: 39 production native libraries, one
build-only Lang seed, and 11 support/tooling crates. There are 90,795 physical
Rust lines under their `src/` directories, including comments and embedded unit
tests, excluding separate integration tests. Native crates account for 69,285
lines. These are scale indicators, not exact removable production-code counts.

There are also 43 non-test Birnam files under `modules/`, plus 13 test/runner
files. Of the 43, 42 declare named modules; `error.birnam` is bootstrap policy.
Two additional Birnam wrappers live under `wrapped/`.

The important distinction is needed before the first Birnam artifacts exist
versus currently loaded unconditionally. [Bootstrap](../../../rust/birnam-bootstrap/src/lib.rs)
and the [Host loader](../../../rust/birnam-host/src/runtime.rs) currently load more
than the first-artifact compiler needs. Removing a native implementation requires
changing startup wiring as well as rewriting its behavior.

The bootstrap classifications below are source/dependency assessments. They are
not experimental proofs obtained by removing each module and rebuilding.

## Recommended sequence and acceptance

1. Port Trace completely, preserving Storage as the snapshot owner.
2. Port Relational, keeping Store unchanged and admitting the authored query layer
   before its first consumers.
3. Port ProjectBuild, using HostProject observations and authored ProjectPolicy.
4. Port HostProject and remove displaced project-support code.
5. Reassess Storage and input/environment wrappers. Handle HostInteraction only
   with an explicit idle-boundary contract.

For each complete port, run a fresh cold installation with the displaced Rust
implementation absent, then installed startup and affected behavior/image checks.
Removing a module only from ordinary startup is insufficient. Keep independent
semantic oracles, current-message dispatch, callback/reentrancy/GC checks and
exact native failure/result behavior. Record focused tests, installation, broader
validation and delivery as separate evidence states.


## Relational conversion assessment — 2026-10-11

**Initial assessment: halted before implementation under the user's stop rule.**
The later [authored slice checkpoint](#authored-positive-query-slice--2026-10-11)
records the implementation subsequently authorized and its performance stop.
This assessment is against `5ef3df60` and the current source. The prior
performance-investigation changes remain separate and untouched. No Relational
implementation, Bootstrap sequence, native inventory or installed runtime was
changed. Relational remains a plausible migration target, but the earlier
recommendation was a dependency assessment, not evidence of a trivial conversion.

The user requested unchanged bootstrap behavior and semantics, and a report and
halt if the conversion is nontrivial or presents unresolved choices. The existing
implementation meets that stop condition: it combines a copied-value query
kernel, a callback-sensitive adapter, canonical identities and early publication.
A direct rewrite using normal collection/equality/arithmetic sends would not
establish equivalence with that Rust implementation. The subsequent user decision
below establishes that this equivalence is not the right requirement for the
kernel's fixed internal operations.

### Decisions resolved by the user

The user clarified that everything in Birnam is late-bound by default and that
the evaluator's fixed internal operations are a smell. Relational queries should
use the current definitions in the world. Equality is intentionally replaceable;
preserving a private frozen equality implementation is not a language invariant.
The same direction applies to ordering and arithmetic used by query evaluation.
Future sends within an in-progress query must respect current definitions,
subject to the existing entered-activation/generation rules.

This explicitly supersedes the initial requirement to reproduce the Rust
kernel's fixed internal operations. Ordinary results, ordering, failure/lifetime
contracts and bootstrap behavior still need validation; unrelated changes are
not authorized by this decision. Intentional identity operations (such as variable
name interning) remain distinct from value matching.

Optimize ordinary semantics with valid dependency checks and deoptimization;
do not create an unreplaceable query-specific primitive floor to preserve the
Rust implementation. Invalid equality/hash contracts are the program's
responsibility. Do not add per-query algebra-law validation, defensive copies
or other costs solely to insulate programs from their own method replacements.
Memory safety, valid roots and exact native failure handling remain required.

The remaining conversion questions concern representation, snapshot membership,
result materialization and bootstrap publication. They are not grounds to retain
frozen Rust query semantics. At this point implementation remained halted;
the next slice below was subsequently authorized and exercised.

### Reference behavior of the current Rust implementation

The crate has 3,043 source lines including tests: 1,598 in the evaluator, 1,124
in the native adapter, 303 in the independent matching tests and 18 in the crate
entry. These line counts are scope indicators, not a performance estimate.

* **Copied-value evaluation.** The adapter classifies inputs using current
  Integer `wordOf:`, Float `bitsOf:`, exact String behavior and String `bytes`
  messages. It copies scalar data before entering the evaluator. Other objects
  remain identity values. See [classification and materialization](../../../rust/birnam-relational/src/native.rs).
* **Fixed matching laws.** The [kernel](../../../rust/birnam-relational/src/evaluator.rs)
  compares Integer only with Integer, Float only with Float, strings by copied
  bytes and other objects by identity. Float NaN does not equal itself; signed
  floating zeroes compare equal. Mixed Integer/Float ordering promotes to Float,
  while equality remains type-strict. Evaluation itself sends no language
  messages.
* **Ordered queries.** Joins, projection, deduplication, disjunction, grouping
  and rules preserve their existing traversal/first-occurrence order. The planner
  schedules binding clauses before dependent filters. Rule relations are rebuilt
  for each query and expanded in definition order, with a 1,000-round cap that
  returns the accumulated relations rather than introducing a new error.
* **Adapter behavior matters.** Scalar projections construct result objects
  through current factories; identity projections retain their original objects.
  The ordinary aggregate API first obtains a materialized `find` result, sends
  `size`/`at:` to that result, and classifies those objects again. Folding directly
  over the internal query result would skip existing callbacks. Empty public
  count/sum return zero; empty public min/max/avg return nil. Integer overflow
  becomes nil at this adapter boundary. These details must not be inferred only
  from the pure aggregate helper.
* **Lifetime and failures.** Snapshot objects and rule vectors stay rooted across
  destructive or collecting Store callbacks. Nested queries have distinct scopes.
  Escaped collectors reject later deliveries; callback failures are remembered.
  Shape errors answer nil, while dependency native failures retain their Outcome.
  The million-triple snapshot bound, 512-element shape bound and four-level pull
  limit are existing behavior, not simplification opportunities.

### Decisions that prevent a mechanical port

| Boundary | Why a straightforward rewrite is unsafe | What must be resolved |
| --- | --- | --- |
| Internal value representation | The existing kernel copies scalars and uses fixed operations; this is now a documented semantic limitation, not the target contract. | Resolved direction: use current world operations for value matching and computation. Specify snapshot membership, rooting and result materialization separately; late binding alone does not settle those contracts. |
| Kernel implementation versus native primitives | Keeping the evaluator behind a renamed native helper would retain both the foreign implementation and its fixed internal semantics. | Resolved direction: authored query algorithms using ordinary late-bound operations. Any transitional Rust dependency needs an explicit removal condition; no permanent foreign-language floor is an architectural goal. |
| LogicVar identity and representation | `named:` interns by name-object identity; `clone`/`new` create distinct objects with the same name. Current objects own a native reference payload, have published behavior identities and a registered reference owner. | Define how an ordinary-slot representation preserves canonical names, clones, exact behavior recognition, owner declarations, reloads and image recovery. A general value-equality Map is not automatically an identity-keyed cache. |
| Bootstrap publication | Relational is loaded immediately after Vector/Map/Store, before Artifact/PEG/TCC/Codegen. Moving it to the later authored-module loop changes when LogicVar, Store query methods and related behaviors become available. | Establish the same externally required publication/readiness behavior in seed and installed startup. A later load cannot be justified solely because common compiler paths appear not to query Store. |
| Execution and cost | Native evaluation currently runs without language callbacks or resumable frames. An authored implementation introduces allocations, sends and potentially different scheduling/observation points. | Specify the admissible execution/observation contract and measured performance acceptance before choosing synchronous versus resumable bodies, caching, indexes or other redesigns. |

The user has authorized changing the kernel's fixed-operation behavior to current
world dispatch. Changing result order, removing existing adapter callbacks,
weakening error/lifetime handling, bypassing current dispatch, or claiming a
renamed Rust evaluator as a completed port are separate changes and are not
implied by that authorization.

### Bootstrap evidence and its limit

[Bootstrap's current order](../../../rust/birnam-bootstrap/src/lib.rs) loads
Execution and Object Model before Relational, but loads the compiler owners after
it. The [installer](../../../rust/birnam-build/src/main.rs) invokes a Rust-seeded host
to compile the earliest Birnam artifacts into an empty prefix. Therefore simply
replacing the early native load with an authored artifact risks requiring an
artifact before the installer has produced it.

The compiler lowers a `?name` literal to an ordinary `LogicVar named:` send
([lowering](../../../rust/birnam-codegen/src/lib.rs)). This supports separating query
algorithms from compilation, but does not prove unchanged early publication or
that every seed/installer path works without the native module. No cold build
with Relational removed was attempted, and no bootstrap-independence claim is
made. Any retained bootstrap seed would need evidence of necessity, a bounded
responsibility, an explicit distinction from the authored production module,
and a path to eventual replacement in Birnam.

### Formal and runtime verification needed after the decisions

The existing [semantic framework](../../../formal/semantics/README.md) explicitly
requires an honest observation contract. Lean cannot make new observable callbacks
or changed Float laws disappear, and TLC cannot choose the intended bootstrap
publication contract. No new conversion-equivalence theorem is claimed here.

Once those boundaries are fixed:

1. Use Lean to specify matching and ordered projection over an explicit
   comparison operation and state/effect transitions. Do not assume equality is
   permanently fixed, pure, reflexive, symmetric or transitive without a justified
   contract. The Rust oracle remains useful only on inputs/operations where the
   intended semantics coincide; it cannot decide replacement-sensitive behavior.
   Extend the authored specification to planning, aggregates, rules and pull.
2. Use TLA+ for snapshot collection, nested query scopes, failure latching,
   escaped collectors, current replacement callbacks and cleanup under GC.
   Model bootstrap readiness separately; require negative cases for late
   publication, stale callbacks and premature root release.
3. Differentially test the compatible subset against the independent Rust
   evaluator, retaining it as test support during migration. Add independent
   tests for live equality/arithmetic/factory replacement, including changes
   during a query, collecting/reentrant providers and exact native failures.
   Record deliberate divergence from fixed Rust operations as required behavior,
   not a failed attempt to reproduce that implementation.
4. Compare bounded representative joins, recursive rules, aggregates and pulls
   before accepting the port. Preserve the current execution policy until its
   replacement is explicitly established; no performance budget has been chosen.
5. Require a fresh empty-prefix cold installation with the displaced production
   library absent, followed by installed startup, compiled logic literals,
   Module reload and mapped/rebuilt image checks. Keeping only an old installed
   artifact or moving a load later does not establish cold-bootstrap parity.

## Authored positive-query slice — 2026-10-11

**Implemented in isolation; further conversion halted on the measured performance
tradeoff.** Canonical Store methods, LogicVar, bootstrap order, native library
inventory and the normal installation are unchanged. Rust remains transitional;
this is not a completed Relational port.

[modules/relational-query.birnam](../../../modules/relational-query.birnam) publishes
an explicitly loaded `RelationalQuery` facade. Its `on:` method attaches an
existing Store, and the resulting facade answers `findAll:where:` for positive
three-term patterns, conjunctions, shared/repeated variables, ordered projection
and deduplication. It depends on stdlib equality and is not in the installer or
bootstrap module lists. Tests compile it through the existing Codegen interface
with synchronous bodies, keeping this first experiment's native call boundary.

### Observable contract of this slice

* The Store determines snapshot membership and delivery order. The collector
  retains original Object references; it does not freeze scalar values or method
  definitions. Subsequent comparisons observe the current world. Projection
  returns the original first-seen objects, including scalar objects and nil.
  This deliberately removes the old kernel's scalar rematerialization behavior.
* Clauses, incoming solutions and facts are scanned in order; fields are tested
  entity, attribute, value. Constants and existing variable bindings send
  `expected = actual`. Unbound variables bind the actual object. Variable names
  are compared by explicit identity, separately from query value equality.
* Deduplication sends `earlier = incoming` in first-seen order and stops at the
  first true answer. There is no identical-object shortcut or validation/repair
  of equality's algebraic laws. A nonreflexive equality may retain repeated
  occurrences of the same Object; the tests require that behavior.
* Native comparison failures escape unchanged; language Errors stop the query
  and retain identity. No later value comparisons run after that failure. The
  rest of normal Boolean/control dispatch remains ordinary Birnam behavior.
* Every invocation owns a fresh collector. It stops accepting facts after
  enumeration, retains the snapshot during evaluation, and clears it on success
  or failure through Execution's existing deferred-send cleanup. Escaped
  collectors cannot affect a later invocation. Nested queries have distinct
  state. No collector contains a pointer to a native test stack in production.
* Reserved predicate/rule/not/or shapes and wrong-width Vector clauses answer
  nil. This is a positive-Vector-pattern subset, not full compatibility for every
  malformed or duck-typed input. History, aggregates, rules, disjunction, negation
  and pull have not been implemented.

The deliberate semantic changes above implement the user's late-binding
clarification. The native evaluator is used only as a reference in compatible
cases; it is not an oracle for overridden equality or projected scalar identity.

### Acceptance and formal evidence

The new [integration test](../../../rust/birnam-siphon/tests/relational_authored.rs)
runs 64 comparisons against the native query implementation over all 16 directed
two-node graphs, covering projection, self/repeated-variable matches, joins and
constant patterns. It also checks nil binding, original scalar identity,
unsupported syntax, current equality overrides, method replacement between
comparisons, changing deduplication behavior, nonreflexive equality, collecting
and reentrant comparisons, exact native/language failures, snapshot retention
after a provider drops its own references, ignored malformed callbacks, expired
collectors and reclamation after success/failure. Development checks passed in
debug mode; the final expanded suite passed in release mode.

[Relational.lean](../../../formal/semantics/lean/Relational.lean) proves the row fold
agrees with a sequential reference matcher for an arbitrary stateful and failing
comparison, stops comparisons after failure/mismatch, preserves bound object
identity, and obeys ordered projection's first-match rule. Concrete theorems
require observation of replacement and nonreflexive equality. They assume
neither pure nor permanently fixed equality. They do not prove the parser, all
joins, native ABI or generated code.

[RelationalQuery.tla](../../../formal/semantics/tla/RelationalQuery.tla) checks two
nested query scopes, live comparison selection, collection, latched failures,
cleanup and expired collectors. Required negative cases expose cached comparison
bindings, shared scope roots, expired callback writes, forgotten failures and
replayed comparisons. The complete formal runner passed **160 Lean theorems,
28 rejected Lean mutations and 105 TLC cases**. Evidence is retained in the
[measurement record](../../measurements/relational-query-slice-20261011.json).

### Performance stop

Eight alternating single-query samples per variant/case used thread CPU timing,
automatic GC and a fixed 16 MiB budget. Compilation and collections between
samples were excluded. The native samples are short and these implementations
have different dispatch and identity semantics: the ratios are descriptive cost
comparisons, not qualified optimizer speedup/regression claims.

| User facts | Query | Rust median CPU | Birnam median CPU | Managed allocation: Rust -> Birnam |
| ---: | --- | ---: | ---: | ---: |
| 8 | One pattern | 0.088 ms | 3.91 ms | 3,336 -> 128,792 bytes |
| 8 | Two-clause join | 0.103 ms | 18.03 ms | 3,416 -> 423,112 bytes |
| 32 | One pattern | 0.214 ms | 15.37 ms | 11,208 -> 453,728 bytes |
| 32 | Two-clause join | 0.248 ms | 183.92 ms | 11,288 -> 3,778,960 bytes |

Store snapshots also contain their ordinary schema facts. Managed allocation
charges exclude native Rust scratch allocations. Thus these numbers do not claim
total-memory parity. They nevertheless expose a substantial cost for the current
authored traversal, calls and temporary data. No CPU profile has yet attributed
percentages to those mechanisms.

This satisfies the user's stop condition before broadening the implementation or
