# Image loading prior art

Follow-up: the subsequent discussion accepted identity-preserving updates, namespace-path matching, and explicit representation compatibility/migration. The architecture record and review notes contain those decisions; the proposals below preserve the research that led to them.

4 November 2026. Documentation and paper review, not a runtime benchmark or implementation. The user clarified that incoming image contents should install or overwrite their corresponding objects in the current world, from a small module to substantial system replacement. Selective symbol/part loading is desired. Identity matching and migration mechanisms are not yet selected.

**Self distinguishes restarting a world from transporting program pieces.** A snapshot supplies the initial world; the VM then runs a post-read action. Snapshots can carry machine code. [Self VM reference](https://handbook.selflanguage.org/2024.1/vmref.html)

The Transporter moves program pieces between worlds through source files. Its module membership is at slot granularity, so several modules may contribute to one object. Creator annotations identify where an object belongs, allowing other references to name it instead of recreating it. Slot annotations distinguish saved contents from initialization expressions. This is a useful precedent for explicit replacement scope and reference resolution, not a requirement to adopt Self's source format or annotation scheme. [Transporter handbook](https://handbook.selflanguage.org/2024.1/howtoprg.html#the-transporter)

**Smalltalk has several relevant mechanisms, not a single image-import rule.** In Pharo, a whole image preserves a running system and is started by a VM. Code packages are a separate mechanism for installing definitions into that system. Monticello versions contain class and method definitions; package extension methods can belong to a package other than the class they extend. [Pharo by Example](https://books.pharo.org/updated-pharo-by-example/pdf/2018-09-29-UpdatedPharoByExample.pdf), [Deep into Pharo](https://books.pharo.org/deep-into-pharo/pdf/2023-09-02-DeepIntoPharo.pdf)

VisualWorks parcels are a particularly close semantic precedent: binary packages carry objects and initialized code-module state, add or replace methods on existing classes, and replace class/namespace/global definitions. The historical implementation also migrates instances for class shape changes. Its term “partial loading” includes postponing definitions whose prerequisites are absent; that should not be equated with arbitrary user-selected symbol loading. Parcels are Smalltalk binary deployment artifacts, not evidence that those systems use Birnam's proposed native executable/shared-library container. [Parcels paper](https://scg.unibe.ch/archive/papers/Mira05aParcels.pdf)

For arbitrary graphs, Pharo's Fuel provides a separate serialization precedent. It can encode a class as a reference to an existing global or serialize its definition in detail, and supports customization hooks and graph materialization. Graph reconstruction and deciding which installed definitions to replace are distinct responsibilities. [Fuel project](https://github.com/theseion/Fuel)

**Compatibility with optimized execution.** Self demonstrates aggressive optimization together with live programming changes: affected optimized code can be invalidated and active execution deoptimized. This supports Birnam's chosen behavioral contract, but does not prove performance for Birnam's AOT-generated C, opaque payloads, or boxed integers. [Dynamic deoptimization paper](https://bibliography.selflanguage.org/_static/dynamic-deoptimization.pdf)

Historical Self results reported some benchmarks within a factor of two or three of optimized C. Those are workload- and implementation-specific historical results, not a promise of C parity or a forecast for Birnam. [Object, Message, and Performance](https://bibliography.selflanguage.org/object-msg-perf.html)

My design inference is that selection, graph reconstruction, target resolution, and publication can largely be load-time work. Ordinary execution can then use direct object references and optimized calls, subject to the already-agreed replacement/invalidation contract. Imported optimized code must validate its assumptions against the receiving world; linking its addresses is not enough. Native artifact packaging does not remove these obligations.

**The costly ambiguity is what “overwrite an object” means.** Updating a method dictionary or an object's compatible payload in place can preserve its identity and existing references. Rebinding a namespace symbol affects subsequent resolution of that symbol; it does not update references already held elsewhere. Redirecting every reference to an arbitrary replacement object is a stronger operation.

Smalltalk's `become:` family addresses that stronger identity problem. Spur uses forwarding objects and a partial read barrier with direct pointers, rather than requiring a universal extra indirection on every access. The implementation depends on cooperation between object representation, generated code, and memory management. [Miranda and Bera, A Partial Read Barrier for Efficient Support of Live Object-Oriented Programming](https://www.researchgate.net/publication/280700144_A_Partial_Read_Barrier_for_Efficient_Support_of_Live_Object-oriented_Programming)

For Birnam, generic rewriting of all pointer-looking words would be unsound: conservative scanning deliberately cannot distinguish every pointer from coincidentally equal native data. Universal identity redirection or layout migration therefore needs its own representation/protocol contract. Object-defined persistence explains how to reconstruct incoming objects; it does not automatically locate every reference in the existing world or make native/C aliases redirectable. This is an inference from the chosen opaque, conservative model, not a claim that replacement is impossible.

**Proposed next contract, not yet agreed:** distinguish selected definitions/state to install from their dependencies. Resolve each dependency to an existing compatible object or an explicitly included new object; do not treat mere reachability as authority to overwrite a dependency. Selective installation need not imply that the OS maps only the selected native functions, but unselected initialization effects must not run merely because the artifact was mapped. Exact ABI and initialization rules remain to design.

The closest combination of precedents is Self's explicit ownership of transported pieces, VisualWorks-style installation/redefinition, and Self-style optimized-code invalidation. We can adopt those principles while preserving Birnam's native artifact model. The next decision is how existing references must behave when a selected object is overwritten, especially if its payload size or representation changes.
